# تجهيز الكتالوج التجريبي للسحابة

المولّد `scripts/deployment/prepare-preview-catalog.mjs` يجهّز ملف SQL للمراجعة قبل تطبيقه على مشروع Supabase المعاينة. تشغيله يقرأ الملفات العامة داخل المشروع ويكتب النتيجة محليًا؛ لا يتصل بقاعدة بيانات ولا يقرأ إعدادات الاتصال أو حسابات `.local`.

الهدف الذي أكده صاحب المشروع: `mnsaaa`، ورقم المشروع `soggnbfxawlwopglghas`. الرقم في ملف SQL والـ manifest لتحديد مقصد المراجعة. PostgreSQL لا يستطيع إثبات هوية مشروع Supabase من هذا التعليق؛ اختيار المشروع الصحيح يتم صراحة في الموصل وقت التطبيق.

## المحتوى

| العنصر                                                       | العدد والحالة                                        |
| ------------------------------------------------------------ | ---------------------------------------------------- |
| الصفوف الدراسية                                              | ٣                                                    |
| المواد                                                       | ٤                                                    |
| المدرسون                                                     | ٤ أسماء تجريبية وصور SVG الموجودة في `public/images` |
| الكورسات                                                     | ٨ مسودات                                             |
| الوحدات                                                      | ١٢                                                   |
| الدروس                                                       | ٣٣ مسودة، بمدد مخططة من البيانات التجريبية           |
| الكورسات أو الدروس المنشورة                                  | صفر                                                  |
| الفيديوهات والحسابات والأكواد والاشتراكات والنتائج المستوردة | صفر                                                  |

المصدر هو البيانات العامة في `src/lib/catalog.ts`، بنفس حقول `scripts/local/seed-local.mjs`. لا يتم تصدير قاعدة التطوير أو إدخال حساباتها. UUID يتولد داخل قاعدة الهدف باستخدام `gen_random_uuid()`، والعلاقات تعتمد على slug والموضع داخل الكورس، فلا توجد معرفات محلية ثابتة.

الكورسات تبقى `draft` وبيئة تسليمها `development`، مثل البذور المحلية. لا توجد أوقات نشر أو إشارات فيديو جاهز. لهذا سيظهر المدرسون في الكتالوج العام، وتظل الكورسات في لوحة الإدارة حتى تجهيز محتواها والتحقق من إعداد التسليم الملائم. إدخال هذه البيانات وحده لا يجعل الدروس قابلة للمشاهدة أو يثبت جاهزية الموقع للنشر.

## التوليد والفحص دون قاعدة

استخدم Node.js `22.19` أو إصدار `22` المتوافق مع `package.json`، من جذر المشروع:

```powershell
node scripts/deployment/prepare-preview-catalog.mjs --project-ref soggnbfxawlwopglghas --check
node scripts/deployment/prepare-preview-catalog.mjs --project-ref soggnbfxawlwopglghas
```

`--check` يفحص أعداد البيانات ومراجعها وصورها ويكوّن SQL والبصمات في الذاكرة، دون كتابة الناتج. التشغيل الثاني يكتب:

- `.local/deployment-preview/preview-catalog.sql`
- `.local/deployment-preview/preview-catalog.manifest.json`

الأمر يعمل من أي مجلد عمل باستخدام مسار السكربت؛ مسارات المصدر والناتج مشتقة من موقعه داخل المشروع. Node `22.19` يدعم استيراد ملف `.ts` المستخدم هنا دون flag إضافي. قد يظهر تحذير `MODULE_TYPELESS_PACKAGE_JSON` بسبب كشف نوع الملف، كما في السكربت المحلي، ولا يحتاج تغيير نوع المشروع لمعالجته.

الـ manifest يحتوي رقم المشروع المقصود، الأعداد المتوقعة، أسماء migrations المطلوبة، وبصمات SHA-256 للسكربت وملف SQL والمصدر والمigrations والصور. نفس رقم المشروع ونفس المصادر ينتجان SQL مطابقًا في كل مرة. تحقق من البصمة قبل تطبيق النسخة التي تمت مراجعتها؛ تغيّر ملف بعد المراجعة يستلزم إعادة توليد ومراجعة.

## الحماية عند التطبيق

ملف SQL معاملة واحدة تبدأ بـ `BEGIN` وتنتهي بـ `COMMIT`. قبل أول إدخال:

1. يثبت إعداد قراءة حديثة ووقت انتظار قصير للأقفال، ويأخذ advisory lock خاص بالبذور التجريبية.
2. يتحقق من وجود migrations الأربعة بأسمائها: `dorosna_product` و`standalone_assessments` و`catalog_delete` و`media_assets`. تواريخ إصدارات التنفيذ السحابي قد تختلف عن أسماء الملفات المحلية، لذلك لا تعتمد المقارنة على هذه التواريخ.
3. يتحقق من وجود الجداول والحقول المطلوبة، ثم يقفل جداول الكتالوج الستة ضد الكتابة المتزامنة أثناء المعاملة القصيرة؛ القراءة العادية تظل متاحة.
4. يرفض التنفيذ بالكامل لو وجد أي صف، حتى المحذوف منطقيًا، في `grades` أو `subjects` أو `teachers` أو `courses` أو `course_units` أو `lessons`.
5. بعد الإدخال، يتحقق من الأعداد ومن بقاء كل الكورسات والدروس غير منشورة ومن عدم وجود فيديو حالي للدروس.

لا يوجد `UPDATE` أو حذف أو دمج أو `ON CONFLICT` لتخطي البيانات الموجودة. فشل أي خطوة يُفشل المعاملة كلها. إعادة التطبيق بعد نجاحها ستتوقف برسالة `preview_catalog_not_empty_existing_data_preserved`، وتُحفظ البيانات السابقة. لو أداة SQL تركت اتصالًا في معاملة فاشلة، أنهها بـ `ROLLBACK` قبل أي أمر تالٍ.

يطبق مسؤول المشروع الملف بعد مراجعة SQL والـ manifest باستخدام موصل Supabase للمشروع المحدد، ثم يقرأ الأعداد والحالات من القاعدة للتحقق الفعلي. توليد الملفات ونجاح الفحص المحلي لا يعنيان أن البيانات طُبّقت على السحابة. لا تشغّل `local:setup` أو migrations المحلية أو reset بغرض تطبيق هذا الكتالوج.

الأقفال تظل داخل المعاملة كما توضح [وثائق PostgreSQL 17](https://www.postgresql.org/docs/17/sql-lock.html)، والمولّد يحافظ على صلاحيات السكيمة الخاصة دون تعديلها. تغييرات الإتاحة التلقائية للجداول عبر Data API مستقلة عن هذا الإدخال؛ تطبيقنا يقرأ السكيمة الخاصة من الخادم، كما توضح [وثائق Supabase عن الوصول المباشر](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically).
