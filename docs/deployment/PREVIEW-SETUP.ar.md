# تجهيز نسخة عرض وظيفية على Netlify وSupabase

آخر مراجعة: ٤ أكتوبر ٢٠٢٦. الهدف: تشغيل نسخة عرض ببيانات تجريبية على **الموارد الموجودة التي حددها المالك**، مع الحفاظ على بيئة التطوير المحلية.

تواريخ التنفيذ السحابية تختلف عن أسماء ملفات SQL المحلية. تم التحقق من السجل والأسماء؛ لا تعاد migrations ولا تعدل ملفات SQL التاريخية لإنشاء نسخة أخرى من الهيكل. `scripts/local/setup-local.mjs` محروس للمحلي؛ لا يشغّل على السحابة بتغيير الرابط. كذلك سكربت الأدمن المحلي لا ينشئ أدمن سحابيًا تلقائيًا.

تم التحقق من **٣٣ جدولًا**؛ RLS مفعّل على **٣٢**، وجدول `runtime_migrations` محمي بصلاحيات الإدارة ولا يملك مستخدم التطبيق وصولًا إليه. الدور `dorosna_server` له `LOGIN` و`NOINHERIT` و`NOBYPASSRLS` و`NOSUPERUSER`. لا يملك `anon` أو `authenticated` وصولًا إلى schema `app_private`. اتصال الإدارة لا يستخدمه الموقع. [أدوار Postgres](https://supabase.com/docs/guides/database/postgres/roles).

نتيجة Security Advisors: **صفر ملاحظات** وقت المراجعة. مراجعة الأداء أظهرت **١٠ ملاحظات INFO عن مفاتيح خارجية غير مفهرسة**، وبعضها تتطابق أعمدته مع بداية مفتاح أساسي قائم، إضافة إلى فهارس غير مستخدمة في قاعدة العرض الجديدة. لا تعني النتيجة أن الأداء خالٍ من الملاحظات؛ تُراجع الحاجة للفهرسة مع الاستعلامات والحمل الفعلي قبل إضافة فهارس مكررة.

### اتصال التطبيق المتبقي

من **Connect → Transaction pooler** نأخذ اسم الخادم الحقيقي والمنفذ من لوحة المشروع، ونراجع اسم الدخول `dorosna_server.soggnbfxawlwopglghas`. كلمة سر الدور تدخل بشكل خاص، وهي مختلفة عن كلمة سر `postgres` ومفتاح API. يبدأ الكود غير المحلي بتوصيلة واحدة لكل instance؛ `DATABASE_POOL_MAX` اختياري من `1` إلى `10`. لا تستخدم prepared statements مسماة مع transaction pooling. [اتصالات Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres).

الاتصال غير المحلي يفرض `rejectUnauthorized: true`، مع جذور Node أو CA موثوقة في `DATABASE_SSL_CA`. يقبل PEM متعددة السطور أو `\n` مكتوبة؛ الشهادة غير الصالحة ترفض قبل الاتصال. الكود يرفض SSL query parameters داخل `DATABASE_URL` مثل `sslmode` و`sslrootcert` و`ssl` و`uselibpqcompat`، ويرفض تجاوز host/port/user/password عبر query parameters. المحلي يحتفظ بإعداداته المحروسة. نجاح هذه الحماية في الاختبارات لا يثبت صحة شهادة وخادم pooler الفعليين؛ الاختبار السحابي ما زال مطلوبًا. [SSL في node-postgres](https://node-postgres.com/features/ssl).

## ٣. الحسابات والمفاتيح

عدد الحسابات السحابية حاليًا **صفر**. في إعدادات **Authentication** نراجع Phone/password وSite URL والـproviders المطلوبة، ثم ننشئ الأدمن عبر المسار الإداري المعتمد ونجرب الحسابات فعليًا. التطبيق يستخدم `phone_confirm: true` من السيرفر ويربط حساب Auth بحساب التطبيق؛ هذا تأكيد إداري للتجربة، ولا يثبت ملكية الهاتف برسالة OTP. [Password Auth](https://supabase.com/docs/guides/auth/passwords)، [Admin createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser).

دعم `sb_secret_...` اتنفذ: المفتاح في `apikey` ولا يوضع في Bearer كأنه JWT. يظل legacy JWT مدعومًا، وaccess token مستقل في Bearer عند وجوده. هذا التوافق تحقق محليًا بترويسات HTTP وهمية؛ Auth الفعلي مع Supabase لم يختبر بعد. المفاتيح السرية للخادم فقط، ولا تدخل في `NEXT_PUBLIC_` أو Git أو بيانات العرض أو الشات. [مفاتيح Supabase](https://supabase.com/docs/guides/getting-started/api-keys).

Site URL يضبط على رابط العرض بعد تأكيد المشروع. `APP_ORIGIN` مستقل ويجب أن يطابق أصل HTTPS المستخدم فعلًا، بدون مسار أو slash أخيرة. إعداد Allow new users to sign up يتراجع مع الإنشاء الإداري قبل تغييره؛ نحافظ على قواعد التسجيل والاستعادة الحالية. بيانات الأدمن تُسلّم للمالك بطريقة خاصة بعد إنشائه ونجاح الدخول. [إعداد روابط Auth](https://supabase.com/docs/guides/auth/redirect-urls).

## ٤. صور المدرسين والكورسات

`src/server/media/image-storage.ts` ينفذ التخزين الدائم عبر Supabase HTTPS باستخدام `SUPABASE_URL` و`SUPABASE_SERVER_KEY` واسم bucket صريح في `SUPABASE_IMAGE_BUCKET`. خارج `DOROSNA_LOCAL_ONLY=1` لا يحفظ الصور على قرص محلي. القراءة والرفع والتنظيف عبر السيرفر، مع UUID ومسار عرض `/media/images/...` وسجل `media_assets`؛ دعم ترويسات المفاتيح الحديثة والقديمة موجود.

حد ملف الرفع **٤ MiB**، وحد جسم multipart **٤ MiB + ٦٤ KiB**. السيرفر يتحقق من الصيغة والحجم والأبعاد، ويحوّل الملف إلى WebP. هذا حد منفذ فعلًا، وتبقى ملاءمته مع حدود Netlify اختبارًا بعد النشر. [حدود Functions](https://docs.netlify.com/build/functions/configuration/).

**المتبقي:** إنشاء bucket خاصة باسم `dorosna-images` لأول مرة، وضبط المتغير، ثم اختبار الرفع والقراءة وتبديل الصورة وإزالة مرجعها وتنظيف رفع فشلت معاملته. لم تُنشأ bucket ولم ينفذ طلب Storage سحابي فعلي في هذه المرحلة. لا نضيف سياسة كتابة عامة؛ إعداد bucket وحده لا يكفي لإثبات عمل الرفع. [إنشاء bucket](https://supabase.com/docs/guides/storage/buckets/creating-buckets)، [صلاحيات Storage](https://supabase.com/docs/guides/storage/security/access-control).

اختبار الصور يشمل استمرارها بعد deploy جديد، وحدود الحجم والنوع والملف التالف، ورفض غير الأدمن، وحالات فشل الخدمة. الصور الثابتة في `public/images` تظل جزءًا من المستودع؛ ملفات `.local/media` لا تُنقل باعتبارها تخزينًا سحابيًا.

## ٥. انتهاء الامتحانات والمتصفح مقفول

`POST /api/internal/deadlines` اتنفذ في Node runtime. يتطلب `APP_JOB_SECRET` من **٦٤ خانة hex** في ترويسة Bearer، ويستدعي `runDueAttempts` بحد ثابت **محاولة واحدة لكل استدعاء**. query أو body لا يزيدان الحد. مهلة الاستعلام **١٠ ثوانٍ لكل statement**، وليست حدًا مضمونًا لزمن الوظيفة كلها. `maxDuration=30` تلميح للمنصة، وحد التشغيل الفعلي يتراجع بعد النشر.

لم تُنشأ Cron أو Vault أو schedule سحابية. `jobs/local-worker.ts` يعمل فقط مع `DOROSNA_LOCAL_ONLY=1`؛ لا نعتمد عليه على Netlify. بعد اختبار endpoint على رابط العرض، نربط Supabase Cron باستدعاء HTTP، بسر مستقل محفوظ في مكان خاص ومتطابق مع إعداد السيرفر. [Supabase Cron](https://supabase.com/docs/guides/cron/quickstart)، [جدولة HTTP وحفظ السر](https://supabase.com/docs/guides/functions/schedule-functions).

تكرار الجدولة يتحدد بعد قياس زمن التنفيذ والتراكم؛ batch واحدة لا تثبت إنهاء عدد كبير من المحاولات في نفس اللحظة. يلزم اختبار انتهاء المحاولة والمتصفح مقفول، والإعادة والتوازي والحساب المعطل، والحفاظ على النتائج وقواعد فتح الواجبات. تحديث حالة المحاولة بـSQL فقط لا يعادل التصحيح الحالي.

## ٧. التحقق المنفذ وحدوده

نجح build المحلي النهائي، شاملًا endpoint المواعيد وتصحيح النصوص، وlint وtypecheck وformat. الواجهة الفعلية اتراجعت في المتصفح بعروض **١٢٨٠، ٤١٢، ٣٩٠، ٣٢٠ px**؛ شملت البحث والفلاتر وradio chips وتطبيق فلاتر الكتالوج من السيرفر وحفظ الثيم، مع الحفاظ على لوحة الأدمن. اتراجع أيضًا حساب طالب محلي جديد وحالة الكورسات الفارغة، وحساب طالب موجود ببطاقات تقدم حقيقية؛ وضوح اسم المدرس وأزرار الدخول والثيم على الموبايل اتأكدوا. هذه مراجعة محلية وليست اختبارًا لرابط Netlify. الرجوع والتقدم في سجل المتصفح والتنقل بالأسهم داخل radio chips لم يختبرا يدويًا ضمن هذه المراجعة.

مجموع حالات التحقق المنفذة **١٤١**: ١٣٨ حالة رسمية و٣ حالات HTTP فعلية محلية:

| التحقق                     | الحالات | الحد العملي للنتيجة                                                                                           |
| -------------------------- | ------- | ------------------------------------------------------------------------------------------------------------- |
| اختبارات المنصة المحلية    | ١٠٨     | تحقق مسارات المنتج والميزات على بيئة التطوير؛ لا يثبت إعداد Auth أو الخدمات السحابية.                         |
| `verify-cloud-config.mjs`  | ١٠      | مفاتيح وترويسات وإعدادات pool وTLS بخدمات وهمية محلية؛ لا يثبت TLS مع pooler الحقيقي.                         |
| `verify-image-storage.mjs` | ١١      | عقد adapter والحدود وحالات الفشل؛ لا يوجد Storage HTTP سحابي فعلي بعد.                                        |
| `verify-deadline-job.mjs`  | ٩       | حماية الوظيفة وحدها الثابت وحالات الاستجابة؛ لا توجد جدولة أو تجربة سحابية بعد.                               |
| HTTP لوظيفة المواعيد       | ٣       | سر غائب أو خاطئ: `403`، وسر صحيح: `200` مع `finalized: 0` وترويسة `no-store`، باستخدام قاعدة التطوير الفعلية. |

بعد تعديل مهلة استعلام الوظيفة أعيدت اختبارات التعلم (٢٠) والتقييمات المستقلة (١٥) ونجحت؛ هذه إعادة تحقق من الحالات القائمة وليست إضافة إلى إجمالي ١٤١. اختبار HTTP يثبت اتصال endpoint بقاعدة التطوير واستجابته عند عدم وجود محاولات مستحقة، ولا يثبت عمل جدولة سحابية أو إنهاء محاولة سحابية في موعدها. تشغيل الاختبارات السابقة لا يعوض تجربة bucket والجدولة والدخول ونشر Next.js الفعليين. تحقق سجل migrations وأعداد الكتالوج وصلاحيات قاعدة Supabase هو تحقق سحابي منفذ بالفعل، مختلف عن اختبارات الاتصال المعلّقة.

## ٨. شروط اعتماد رابط العرض

قبل تسليم الرابط كنسخة وظيفية:

- build ناجح على Netlify وNode المعتمد، وSSR والـAPI يعملان دون الاعتماد على ملفات `.local`.
- اتصال pooler وTLS بالمستخدم المقيد يعمل؛ صلاحيات `app_private` تظل محجوبة عن المستخدم العام.
- إنشاء الأدمن وطالب تجريبي والدخول والخروج والاستعادة والتعطيل تعمل؛ cookies آمنة على HTTPS وقواعد Origin محفوظة.
- الصور تعمل وتستمر بعد redeploy، مع تحقق الحجم والصيغة والصلاحيات وحالات فشل Storage.
- جدولة حقيقية تنهي الامتحان والمتصفح مغلق، مع اختبار الإعادة والتوازي والتراكم.
- الكورسات والأكواد والواجبات والتقييمات المستقلة والتعديل والحذف تعمل على بيانات العرض، مع حفظ التاريخ المطلوب.
- البحث والفلاتر والدارك مود وRTL والموبايل يعملون على الرابط؛ بيانات الأدمن تسلم بشكل خاص بعد اختبارها.
- الفيديو مربوط بمصدر معتمد ومختبر، أو يظهر بوضوح أنه لم يجهز بعد؛ لا تعلن مشاهدة أونلاين قبل التحقق.

قبل التشغيل الفعلي مع الطلاب يلزم أيضًا قياس الحمل المتوقع، ومراقبة حدود الخدمات، وتجربة الاستعادة من نسخة احتياطية، ومراجعة بيانات الطلاب والفيديو. اكتمال الهيكل والكتالوج وحدهما لا يثبت اكتمال هذه المتطلبات.
