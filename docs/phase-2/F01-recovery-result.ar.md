## السلوك الذي تحقق

| الفحص | النتيجة الفعلية |
|---|---|
| R01 الصلاحيات | أربع جداول خاصة، RLS مفعّل ومفروض. `anon` و`authenticated` و`service_role` بلا صلاحية على schema التجربة. خادم التجربة يعمل بدور اتصال مؤقت بلا superuser أو تجاوز RLS؛ قراءة `auth.users` وحذف سجل التدقيق مرفوضان. |
| R02 الأجهزة والجلسات | جهازان دخلا معًا. المتصفح التجريبي أخذ رمز جلسة عشوائيًا، `HttpOnly` و`SameSite=Strict` و`no-store`. لا JWT أو refresh token أو مفتاح مزود في الاستجابة. |
| R03 تزوير الدور | كتابة `role=admin` في `user_metadata` نجحت لدى Auth، لكن بوابة المنصة ظلت ترى الطالب `student` من الجدول الخاص؛ الاستعادة الإدارية أعادت `403`. طلب مجهول `401`، وطلب بلا مرجع تحقق صحيح `400`، ومصدر أجنبي `403`. |
| R04 إصدار المنحة | الأدمن أصدر رمزًا 256 بت لمدة تجريبية 15 دقيقة، مخزنًا كـSHA-256 فقط. زاد `auth_epoch`، وقفل الاستعادة، وأبطل جلستي المنصة. |
| R05 الجلسات المباشرة | JWT القديم لكل جهاز رُفض بـ`403 session_not_found` عند تغيير كلمة السر، وتغييرها مع كلمة السر القديمة، وتغيير الهاتف، وتغيير البريد، وفصل هوية الهاتف. refresh token رُفض بـ`400 refresh_token_not_found`. الدخول المباشر مجمد بـ`user_banned`. |
| R06 سباق تبادل الرمز | طلبان متزامنان: واحد `200` والثاني `400`. الرمز الخاطئ وإعادة استخدام الرمز الصحيح مرفوضان. |
| R07 الجلسة المحدودة | cookie الاستعادة لا تفتح `/me` أو الاستعادة الإدارية. رُفض مصدر أجنبي، وكلمة ضعيفة، ومحاولة إضافة معرف طالب آخر؛ بقي حساب الطالب الآخر بكلمة سره الأصلية. |
| R08 سباق تغيير كلمة السر | طلبان بكلمتين مختلفتين: نجاح واحد، وطلب تغيير واحد فقط إلى Auth. الكلمة القديمة وكلمة الطلب الخاسر مرفوضتان. كلمة الطلب الفائز دخلت على جهازين جديدين؛ JWT القديم ظل مرفوضًا، والهاتف والبريد لم يتغيرا. |
| R09 الانتهاء والتجديد | إصدار متداخل أثناء عمل المزود رُفض `409`. الرمز المنتهي، والمنحة السابقة بعد تجديدها، وcookie الاستعادة بعد انتهاء مدة المنحة رُفضت. انتهت الصلاحية بتعديل ساعة fixture في قاعدة البيانات، دون انتظار 15 دقيقة. |
| R10 الحساب المعطل | تغيير كلمة السر نجح، لكن الحالة بقيت `disabled`، والدخول إلى بوابة المنصة وإلى Auth بقي مرفوضًا. |
| R11 النتيجة غير المؤكدة | Auth غيّر كلمة السر فعليًا، ثم حُقن فشل قبل تأكيد البوابة. النتيجة `503 review_required`، والمنحة `review_uncertain`، والحساب مقفول، والمزود ما زال مجمدًا. إعادة التغيير وإصدار منحة أخرى رُفضا، ولم يحدث طلب تغيير ثانٍ. |
| R12 التدقيق | 23 حدثًا سجلت الأدمن والطالب ومرجع التحقق والوقت. لا كلمات سر أو رموز أو مفاتيح في السجل. جداول التجربة بلا أعمدة كلمات سر أو JWT أو refresh token. رفضت البوابة وضع الرمز في URL أو تغيير كلمة السر بطلب GET. |

الفحص المستقل السابق للبوابة أكد أربع نقاط على Auth حقيقي: تجميد الأدمن، رفض تغيير كلمة السر والهاتف والبريد من JWT القديم، استمرار التجميد أثناء تعيين كلمة السر الجديدة، ثم نجاح الدخول بالكلمة الجديدة بعد فتح الحساب صراحةً. هذه الفحوص تكمل بعضها، وليست اختبارات قبول مستقلة للمنصة كلها.

## طريقة التنفيذ وحدودها

المتصفح يحصل على جلسة منصة عشوائية، بينما بيانات جلسة Auth تبقى في ذاكرة الخادم التجريبي. كل طلب محمي يفحص الجلسة وصلاحيتها و`auth_epoch` وحالة الحساب ودوره من الجداول الخاصة. لا تعتمد صلاحية الأدمن على `user_metadata` أو جسم الطلب. للبوابة أربعة مسارات كتابة فقط: الدخول، إصدار الاستعادة، تبادل الرمز، وتعيين كلمة السر. لا واجهة أو دروس أو دفع في الخادم التجريبي.

إصدار الاستعادة يثبت قفل الحساب وإبطال جلسات المنصة أولًا بمعاملة قصيرة. بعد ذلك يغيّر الأدمن كلمة سر Auth إلى قيمة عشوائية تُنسى فورًا، ويجمد الدخول عبر واجهة الأدمن المدعومة. **بمجرد نجاح الإصدار، كلمة السر السابقة لا تعود صالحة حتى لو انتهى رمز الاستعادة.** انتهاء الرمز يترك الحساب مقفولًا، ويمكن للأدمن إصدار منحة بديلة بعد التحقق؛ الحالات غير المؤكدة تتطلب مراجعة قبل التجديد.

دليل المصدر للإصدار المستخدم: تحديث كلمة السر إداريًا يستدعي `UpdatePassword` دون استثناء جلسة، و[تنفيذ Auth v2.197.0](https://github.com/supabase/auth/blob/v2.197.0/internal/models/user.go) يلغي الجلسات في هذا المسار. رفض الجلسة القديمة لدى Auth يطابق [فحص session_id في مصدر الإصدار نفسه](https://github.com/supabase/auth/blob/v2.197.0/internal/api/auth.go). اعتمدنا أيضًا على النتيجة المرصودة، وليس قراءة المصدر وحدها.

تبادل الرمز يربطه بـcookie محدودة وبالطالب الموجود في المنحة، ويمنع تبادلًا آخر. تعيين كلمة السر يحجز عملية واحدة تحت قفل حساب وصف منحة، ثم يطلب التغيير من Auth خارج معاملة قاعدة البيانات. للحالة مراحل `preparing → issued → exchanged → claimed → applied → consumed`. فشل التأكيد ينقلها إلى `review_uncertain` أو يبقي مرحلة محجوزة عند تعذر قاعدة البيانات؛ لا يعاد طلب التغيير تلقائيًا بكلمة أخرى. الطلبات المباشرة ليست معاملة واحدة مع قاعدة بيانات المنصة، ولذلك لا يمثل نجاح هذا المسار اكتمال معالجة جميع أنواع انقطاع الخادم.

الحساب النشط يفتح لدى المزود بعد نجاح تعيين الكلمة؛ الحساب المعطل يبقى مجمدًا. استخدم نموذج الاختبار `876000h` كتجميد طويل يمنع الفتح التلقائي أثناء التجربة، **وهذا ليس قرار مدة أو سياسة للإنتاج**. لا تحفظ كلمة السر الجديدة لإعادة محاولة الطلب، ولا تكتب مفاتيح المزود في ملفات المتصفح أو النتائج.

مدة المنحة والجلسة 15 دقيقة قرار اختبار فقط. cookies هنا فوق HTTP محلي على `127.0.0.1`، لذلك لم توضع `Secure`؛ إثبات HTTPS و`Secure` وسياسة الجلسات الإنتاجية باقٍ. يوجد فحص مصدر الطلب ورفض المصادر الأجنبية، لكن هذه النتيجة لا تغلق اختبارات CSRF والمتصفح كلها.

رفض JWT القديم في **Auth** لا يساوي إبطال توقيعه في كل خدمة تقبل JWT. [توثيق جلسات Supabase](https://supabase.com/docs/guides/auth/sessions) يوضح اختلاف عمر access token وإلغاء الجلسة. لم تعمل Data API أو Storage في هذه الدفعة؛ أثبتنا سحب صلاحيات أدوار العميل من schema الخاصة وفحص RLS، ولم ندّع اختبار بقية الخدمات مباشرة. إثبات الخدمة المستهدفة، وخاصة Supabase المُدار وإعداد الهاتف دون SMS، باقٍ قبل اعتماد التقنية.

## فحص قاعدة البيانات والحالة النهائية

`supabase db advisors --local --type all --level info --fail-on error` انتهى برمز `0` وأبلغ `No issues found`. الإصدار `2.119.0` لم يعِد جسم JSON لهذه النتيجة الفارغة؛ سجل التحقق يذكر هذا صراحةً. صلاحيات الجدول وRLS ودور الاتصال اختبرت أيضًا باستعلامات ورفض طلبات فعلية.

SQL موجود داخل مجلد التجربة، وطبق محليًا بأمر `db query --local --file`. ملفه عبارة عن جملة `DO` واحدة ذرية، لأن هذا الإصدار رفض ملفًا يحوي عدة أوامر منفصلة في prepared statement. لم تُنشأ migration نهائية أو schema F03. أضيفت `pg@8.23.1` بإصدار مثبت في lockfile؛ تدقيق npm وقت التثبيت وجد صفر ثغرات في 23 حزمة.

التنظيف النهائي:

- أزيلت حسابات Auth الوهمية الخمسة، وتأكدت `404` بعدها، مع فحص ملكية كل حساب لـrun الاختبار قبل الحذف.
- الجداول التجريبية الأربع فارغة؛ لا حسابات أو جلسات أو منح أو أحداث وهمية متبقية. الحذف يخص بيانات الاختبار فقط، ولا يمثل سلوك حذف تاريخ الطالب في المنتج.
- دور الاتصال المؤقت أزيل، وخادم Node التجريبي أغلق. يبقى الدور `dorosna_auth_spike_server` بلا LOGIN، والجداول الفارغة لتكرار التجربة.
- Postgres وAuth وKong ما زالت `healthy`. منافذ الجهاز محصورة على `127.0.0.1:54322` و`127.0.0.1:54321`؛ Auth داخلي بلا منفذ منشور.
- لم تنشأ بيانات طالب أو اشتراكات حقيقية أو خدمة سحابية أو نشر. التغييرات السابقة في Figma والمرحلة الأولى محفوظة.

## ما بقي في F01 والمجموعة التالية

هذه أدلة فعلية لأجزاء من T01 وT05–T12 في [خطة القبول الأصلية](F01-auth-proposal.ar.md)، ولا تستبدلها كلها:

- T01–T04: التسجيل الكامل مع الاسم والصف، توحيد صيغ الهاتف والمدخلات العربية، التسجيل المتزامن، الأخطاء الموحدة، وفشل إنشاء Auth أو الملف وإعادة الطلب وتسويته.
- T08–T09: توقف العملية في كل مرحلة وتسوية العملية غير المؤكدة من الأدمن، الطلبات المباشرة إلى Auth التي اجتازت فحص الجلسة **قبل** تجميد الحساب، والوصول الفعلي إلى Data API وStorage. هذه الحالات لم تختبر هنا ولا يجوز افتراض نجاحها.
- T10–T12: دمج دورة تعطيل الحساب وتغيير الحالة بالتزامن مع الاستعادة، استمرار سجل المنتج الحقيقي، سياسة انتهاء وتجديد جلسات الإنتاج، اختبار متصفح مع HTTPS، وحدود التخمين للمداخل العامة وللرمز المؤقت.

**تحديث بعد الدفعة التالية:** وافق المستخدم على المجموعة المقترحة ونُفذت. [تقرير التسجيل والأعطال](F01-registration-result.ar.md) يسجل نجاح 12 مجموعة فحص، و10 مراحل توقف فعلي للعملية، ومنع التخمين وطلبات PostgREST المباشرة، مع تنظيف الحسابات الوهمية. كشف أيضًا نجاح طلب Auth اجتاز التحقق قبل التجميد؛ لذلك رفض JWT في طلب جديد الوارد في هذه الوثيقة لا يكفي وحده. نجح قيد على Auth في Kong المحلي، ولم يثبت مكافئه في Supabase المُدار. نُفذت فحوص الاستعادة الاثنا عشر مجددًا خلال التمديد المحلي قبل تفعيل هذا القيد؛ النتائج JSON قابلة للتحديث عند الإعادة، بينما أقسام هذه الوثيقة تصف نطاق الدفعة السابقة. F01 تبقى مفتوحة للقيود الموضحة في التقرير الأحدث.
