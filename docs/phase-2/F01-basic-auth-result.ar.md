# F01 — نتيجة تجربة الهاتف وكلمة السر المحلية

تاريخ التنفيذ: **2026-10-02 بتوقيت القاهرة**.

**نجح المسار الأساسي محليًا: 11 فحصًا ناجحًا و0 فشل في التشغيل النهائي، مع إبطال جلسات الحساب التجريبي وحذفه. F01 ما زالت مفتوحة.**

هذه نتيجة المجموعة التي وافق عليها المستخدم «اه اشتغل» بعد [تركيب الأدوات](F01-tooling-install-result.ar.md): إعداد وتشغيل الخدمات المحلية، وتجربة إنشاء حساب هاتف وكلمة سر والدخول دون SMS، والتكرار وأخطاء الدخول والتسجيل العام والخروج. لا توجد واجهة منصة أو بيانات طالب حقيقية في هذه التجربة.

المخرجات القابلة للمراجعة:

- [نتائج الاختبار المنقحة](F01-basic-auth-results.json): حالات HTTP، الأدلة، وقت التشغيل، صور الحاويات، منافذها، ونتيجة التنظيف.
- [كود الاختبار](../../experiments/auth-spike/scripts/auth-basic.mjs).
- [دليل تشغيل التجربة](../../experiments/auth-spike/README.ar.md)، و[إعداد Supabase](../../experiments/auth-spike/supabase/config.toml).

## 1. السلوك الذي اختبر فعليًا

| الفحص | النتيجة المرصودة |
|---|---|
| B01 جاهزية Auth | `/health` أعاد `200` والإصدار `v2.197.0`. |
| B02 الإعداد الفعلي | `/settings`: التسجيل العام مقفول، مزود الهاتف مفعّل، مزود البريد مقفول، و`phone_autoconfirm = true`. |
| B03 الإنشاء من الخادم | طلب أدمن أنشأ هاتفًا وكلمة سر بـ`phone_confirm: true`، دون بريد أو OTP؛ `200`، ودور Auth الناتج `authenticated`. |
| B04 الدخول | الهاتف وكلمة السر أعادا جلسة وهوية الحساب الصحيح؛ `200`. |
| B05 فحص الهوية | token الدخول أعاد حساب Auth نفسه من `/user`؛ `200`. |
| B06 أخطاء الدخول | كلمة سر خاطئة ورقم غير موجود أعادا الرسالة نفسها و`400 invalid_credentials`. |
| B07 رقم مكرر | إنشاء أدمن ثانٍ أعاد `422 phone_exists`؛ ظل الحساب واحدًا، وكلمة سره الأصلية صالحة، والكلمة البديلة مرفوضة. |
| B08 التسجيل العام | محاولتا التسجيل بهاتف وبريد أعادتا `422 signup_disabled`. |
| B09 صلاحية إنشاء الحساب | المفتاح العام فشل في إنشاء حساب من مسار الأدمن بـ`403 not_admin`. |
| B10 الخروج المحلي | الخروج أعاد `204`؛ refresh token الخاص بالجلسة أصبح مرفوضًا بـ`400 refresh_token_not_found`. |
| B11 الدخول بعد الخروج | نجح الدخول من جديد بكلمة السر الأصلية، وأعاد جلسة جديدة؛ `200`. |
| التنظيف | خروج عام لجلسات الحساب `204`، ثم حذف الحساب `200`، ثم جلبه أعاد `404 user_not_found`. |

الكلمات والرموز والمفاتيح بقيت في ذاكرة الاختبار، ولم تكتب في JSON. مسارات المستخدم في سجل الطلبات استبدل فيها المعرف بـ`[test-user]`.

## 2. الخدمات والإعدادات المستخدمة

| الخدمة | الإصدار المختبر | الوصول من الجهاز |
|---|---|---|
| Supabase CLI | `2.119.0` مثبتة في lockfile | أداة محلية داخل مجلد التجربة. |
| Postgres | `public.ecr.aws/supabase/postgres:17.11.0.002` | `127.0.0.1:54322` فقط. |
| Auth | `public.ecr.aws/supabase/gotrue:v2.197.0` | داخل شبكة Docker على 9999، عبر gateway فقط من الجهاز. |
| Kong | `public.ecr.aws/supabase/kong:2.8.1` | `127.0.0.1:54321` فقط. |

الخدمات الثلاث كانت `healthy` بعد التشغيل. لا Studio أو PostgREST أو Storage أو Realtime أو Edge Runtime أو Analytics أو خادم بريد محلي. سحب الصور واجه رسائل rate limit مؤقتة من السجل، ثم اكتمل التشغيل بنجاح.

الإعداد: التسجيل العام `false`، تأكيد الهاتف `false`، ولا مزود SMS أو بيانات اعتماده أو SMTP خارجي؛ حد كلمة السر 12 مع متطلبات الحروف والأرقام والرموز، ومدة JWT 900 ثانية. لم يطلب مسار الإنشاء أو الدخول OTP أو بريدًا، ولم ينفذ الاختبار طلب إرسال رسالة. `phone_confirm: true` قبول تقني من الخادم، وليس إثبات ملكية الرقم.

مفاتيح Auth المحلية قرئت من CLI داخل العملية. قد تعرض CLI المفاتيح في مخرجات البدء، لذا حفظت المخرجات الخام تحت `.local` المتجاهلة في Git. لا مشروع Supabase سحابي أو حساب أو مفتاح إنتاج أو خدمة مدفوعة مستخدمة هنا.

## 3. ضبط تشغيل محلي لازم لهذه النتيجة

النتيجة تخص **نسخة Auth المحلية مع مشغّل التجربة**؛ ملف TOML وحده مع `supabase start` الخام لم يحقق شروط التجربة في الفحص المنفذ.

1. CLI `2.119.0` عطلت دخول الهاتف تلقائيًا عند عدم وجود مزود SMS. روجع [مصدر start للإصدار نفسه](https://github.com/supabase/cli/blob/v2.119.0/apps/cli/src/commands/start/start.handler.ts)، ثم ضبط مشغّل Docker المحلي `GOTRUE_EXTERNAL_PHONE_ENABLED=true` عند إنشاء حاوية Auth، مع بقاء مزود SMS غير configured. تأكد الاختبار من إعداد الحاوية ومن إعداد API الفعلي ونجاح الدخول.
2. أنشئت شبكة بخيار ربط 127.0.0.1 كما في [دليل Supabase المحلي](https://supabase.com/docs/guides/local-development)، لكن فحص الحاويات في التشغيل الأول أظهر `0.0.0.0` و`::` للمنافذ المنشورة. أوقفت الحاويات قبل إنشاء أي حساب، مع الاحتفاظ بالـvolume. مشغّل التجربة يمرر `-p 127.0.0.1:...` صراحةً؛ أكد الفحص النهائي ربط API وPostgres بـ127.0.0.1.

ملفات الضبط: [start-local.ps1](../../experiments/auth-spike/scripts/start-local.ps1)، و[DockerShim.cs](../../experiments/auth-spike/scripts/DockerShim.cs)، و[docker-local.mjs](../../experiments/auth-spike/scripts/docker-local.mjs). المشغّل مبني بأداة C# الموجودة في Windows، ويمرر المعاملات والمخرجات مباشرة دون shell. التعديل يخص حاويات التجربة الثلاث، ولم يعدل CLI أو Docker المثبتين أو PATH الدائم أو توزيعة Ubuntu.

هذه تجربة قابلة للتكرار على الجهاز الحالي، وليست إثباتًا لإمكان تطبيق الإعداد ذاته على Supabase المُدار أو اعتمادًا لترتيب تشغيل إنتاج. إعداد الخدمة المستهدفة يحتاج مراجعة وإثباتًا قبل اختيار التقنية نهائيًا. دعم الهاتف وكلمة السر ووسيلة الإنشاء الإداري راجعت في [مرجع password Auth](https://supabase.com/docs/guides/auth/passwords)، و[مرجع createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser)، و[مصدر Auth وواجهاته](https://github.com/supabase/auth).

## 4. ما بقي لإغلاق F01

هذه الفحوص B01–B11 تثبت أساسًا جزئيًا من [خطة T01–T12](F01-auth-proposal.ar.md). لا تغلق اختبارات المنصة الأصلية:

- T01 يحتاج ربط ملف المستخدم ومسار خادم المنصة؛ الموجود الآن حساب Auth فقط.
- T02 يحتاج توحيد صيغ الرقم والمدخلات العربية والتزامن؛ اختبر هنا تكرار الرقم الدولي نفسه فقط.
- T03 يحتاج الفشل الجزئي للتسجيل وإعادة الطلب وتسوية الهوية والملف.
- T04 وT05 يحتاجان سلوك خادم المنصة، ومنع تزوير الأدوار والوصول إلى بيانات مستخدم آخر؛ الموجود دليل رفض محدود من Auth.
- T06–T09 يحتاجون الاستعادة الحضورية ورمزًا مؤقتًا لمرة واحدة، وسباقات التنفيذ، ومنع الجلسات القديمة والتغيير المباشر عبر JWT.
- T10–T12 يحتاجون تعطيل الحساب والأجهزة المتعددة وcookies ومصادر الطلب والتخمين.

إبطال refresh token بعد الخروج **لا يثبت إبطال access JWT قبل انتهاء مدته**. لم يختبر هنا استخدام JWT قديم لتغيير كلمة السر أو الهاتف أو الهوية مباشرة، ولا API بيانات المنصة. لم تنشأ جداول المنصة أو schema نهائية أو شاشة مستخدم.

## 5. الحالة النهائية والمجموعة التالية للموافقة

خدمات التجربة الثلاث ما زالت تعمل على localhost. الحساب الوهمي وجلساته أزيلت. Ubuntu ما زالت `Stopped`، والمساحة المتاحة على C في الفحص اللاحق `47.86 GiB`. لم تغير ميزات Windows أو تحدث WSL أو تشغل Ubuntu أو تنشر شيئًا. التغييرات السابقة في Figma والمرحلة الأولى محفوظة.

المجموعة المقترحة هنا **نُفذت لاحقًا بعد موافقة المستخدم «موافق كمل يلا»**؛ نتيجتها في [تقرير الاستعادة](F01-recovery-result.ar.md). نطاق الموافقة كان: إثبات مسار خادم المنصة والاستعادة الحضورية داخل التجربة نفسها، بما يشمل إنشاء بيانات مستخدم وجلسات تجريبية خاصة، ومنحة محدودة ذات مدة وصلاحية استعمال واحد، وتعيين كلمة سر جديدة من مسار الأدمن، وتسجيل الحدث دون أسرار، واختبار إعادة استخدام المنحة والجلسات القديمة ومحاولات تعديل كلمة السر والهاتف مباشرة عبر JWT. لم يتضمن بيانات طالب أو اشتراكات فعلية أو schema المنصة النهائية أو واجهة إنتاج أو Bunny أو نشرًا.
