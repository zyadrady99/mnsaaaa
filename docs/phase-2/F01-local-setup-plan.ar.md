# F01 — خطة تجهيز التجربة المحلية للمراجعة

تاريخ المراجعة: **2026-10-02 بتوقيت القاهرة**.

**الحالة: فحص المواصفات ومراجعة المتطلبات وتجهيز هذه الخطة مكتمل؛ التثبيت والتشغيل ينتظران الموافقة.** توجد مؤشرات مناسبة لمحاولة تجهيز Docker باستخدام WSL 2. لم يُختبر تشغيل محرك أو حاوية، فلا يوجد اعتماد نهائي للتوافق التشغيلي بعد.

هذه الوثيقة تكمل [تقرير الأدوات](F01-local-readiness.ar.md) و[مقترح الحسابات وخطة الاختبار](F01-auth-proposal.ar.md). نطاق الموافقة لهذه الدفعة كان فحص مواصفات الجهاز والمتطلبات الرسمية وحفظ خطة التثبيت فقط. لم يثبت Docker أو CLI أو أي حزم؛ لم تتغير ميزات Windows أو BIOS أو WSL، ولم تشغل Ubuntu أو خدمات Supabase.

## 1. نتائج الجهاز الفعلية

| العنصر | النتيجة المرصودة | الأثر على الخطة |
|---|---|---|
| النظام | Windows 11 Home، نسخة `10.0.26200`، بناء `26200`، 64-bit؛ أظهر WSL الإصدار الكامل `10.0.26200.9457` | نختار أدوات Windows x64 ومسار حاويات Linux. |
| المعمارية | `x64-based PC` | لا نستخدم إصدار ARM التجريبي. |
| المعالج | Intel Core i7-14650HX؛ 16 نواة و24 logical processor | لا يقترح تحديث عتاد بناءً على هذا الفحص. |
| الذاكرة | `15.71 GiB` كما أبلغ النظام، أي نحو 16 جيجا | أعلى من حد RAM البالغ 8GB في متطلبات Docker؛ الاستهلاك الفعلي للتجربة يقاس بعد تشغيلها. |
| مساحة C المتاحة | `49.29 GiB` من `474.72 GiB` وقت الفحص | توجد مساحة للتجهيز الأولي، لكن لم نقس حجم التنزيلات أو الصور أو القرص الافتراضي. يعاد فحص المتاح قبل التنفيذ. |
| WSL | `2.6.3.0`، kernel `6.6.87.2-1` | يتجاوز حد Docker الموثق `2.1.5`. لا يقترح تحديث WSL من أجل التجربة الحالية. |
| توزيعة موجودة | `Ubuntu-24.04`، حالتها `Stopped`، نسختها WSL `2`؛ الإصدار الافتراضي أيضًا `2` | لم تشغل أو تفحص ملفاتها. لا يلزم تثبيت Ubuntu إضافية. |
| Virtual Machine Platform | `InstallState = 1`، مفعلة | لا نقترح تفعيل هذه الميزة من جديد. |

| خدمة LanmanServer | `Running`، بدء `Auto` | يطابق الوضع المذكور في دليل Docker. لم نشغل أو نعدل الخدمة. |
| Docker Desktop في موضع المستخدم | المجلد `C:\Users\zyadrady\AppData\Local\Programs\DockerDesktop` وملفا التطبيق وCLI غير موجودة | فحص إضافي لمسار التثبيت الموثق حديثًا، يؤكد عدم العثور على Docker في هذا المسار أيضًا. |

مصدر شروط RAM ونسخة WSL ومسار التثبيت: [دليل Docker على Windows](https://docs.docker.com/desktop/setup/install/windows-install/). تفاصيل تشغيل أوامر Docker من Windows دون توزيعة Linux مخصصة: [دليل WSL backend](https://docs.docker.com/desktop/features/wsl/).

حقول CIM الخاصة بالمعالج `VirtualizationFirmwareEnabled` و`SecondLevelAddressTranslationExtensions` و`VMMonitorModeExtensions` رجعت `false`، بالتزامن مع `HypervisorPresent = true`. نسجل هذه النتائج كما هي؛ لا نستنتج منها حاجة لتغيير BIOS. اختبار تشغيل Docker بعد الموافقة هو الدليل التالي المطلوب. إذا ظهر رفض متعلق بالمحاكاة الافتراضية، يسجل الخطأ ويعرض الإصلاح المحدد قبل تغيير إعدادات الجهاز.

تعذر بعض فحص CIM و`wsl --status` داخل قيود تنفيذ Codex بسبب `Access denied`، ثم نجح نفس فحص القراءة بعد السماح بتنفيذه خارج تلك القيود. هذه الأخطاء ليست دليلًا على تلف WSL أو عدم امتلاك المستخدم صلاحيات على جهازه. أوامر WSL المستعملة كانت عرض الإصدار والحالة وقائمة التوزيعات فقط، كما في [مرجع Microsoft للأوامر الأساسية](https://learn.microsoft.com/en-us/windows/wsl/basic-commands).

## 2. الأدوات والإصدارات المقترحة

| الجزء | المقترح المراجع | دليل الإصدار أو المتطلب |
|---|---|---|
| Node وnpm | استخدام Node `22.19.0` وnpm `10.9.3` الموجودين في `C:\Program Files\nodejs` لهذه التجربة فقط | فحص محلي سابق نجح. دليل CLI يشترط Node 20 فأعلى؛ هذا يطابق الحد، دون ادعاء نجاح جميع الحزم قبل تثبيتها. |
| Docker Desktop | **`4.93.0`، Windows x64، per-user، backend WSL 2** | [الإصدار الرسمي](https://docs.docker.com/desktop/release-notes/#4930)، بتاريخ 2026-09-28. |
| Supabase CLI | **`2.119.0`**، اعتماد تطوير بإصدار دقيق داخل مجلد تجربة منفصل | [الإصدار الرسمي](https://github.com/supabase/cli/releases/tag/v2.119.0)، بتاريخ 2026-09-30؛ وتحقق `npm view` من وجود نفس الإصدار في سجل npm. |
| طريقة تركيب CLI | `npm install --save-dev --save-exact supabase@2.119.0` داخل مجلد التجربة | [دليل Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started) يدعم اعتماد التطوير وإصدارات مثبتة؛ لا ننشئ أمرًا عامًا على مستوى الجهاز بهذه الطريقة. |

مجلد التجربة المقترح: `experiments/auth-spike` داخل المشروع. الملفات التي قد تنشأ بعد الموافقة على تركيب CLI: `package.json` خاص بالتجربة، و`package-lock.json`، و`.gitignore` محلي لتجاهل `node_modules` وملفات البيئة. لا تنشأ حاليًا ملفات Next.js أو هيكل تطبيق نهائي؛ ذلك في F05 بعد اعتماد التقنية.

تستعمل أوامر npm المسار الموجود مباشرة، ويثبت اختيار Node للعملية نفسها عند الحاجة؛ لا تعديل دائم لـPATH ولا إعادة تثبيت Node/npm. بعد تركيب CLI يستعمل wrapper الموجود تحت `node_modules/.bin`، مع `--version` و`--help` أولًا قبل أي `init` أو تشغيل. لا يعتمد `npx` الذي قد ينزل إصدارًا آخر تلقائيًا.

## 3. تنزيل Docker والتحقق منه

التنزيل المقترح من رابط Windows في قسم الإصدار `4.93.0` الرسمي، إلى مجلد مؤقت خاص بالتجهيز. لا يضاف installer إلى ملفات المشروع.

قيمة SHA-256 المنشورة التي تمت قراءتها للملف `Docker Desktop Installer.exe`:

```text
c139124c9cf71477dc565c3c0ea5a18f90b93d68ebe9aaa848a065960416c0bc
```

المصدر: [ملف checksums الرسمي، build 240920](https://desktop.docker.com/win/main/amd64/240920/checksums.txt). بعد التنزيل يقارن hash الملف بهذه القيمة وتراجع هوية التوقيع. التعارض يوقف التركيب؛ لا نعوضه باستعمال ملف أو إصدار مختلف دون مراجعة. **لم ينزل installer في هذه الدفعة.**

قراءة بيانات npm العامة نجحت خارج قيود الشبكة بعد أن رفضها sandbox. الإصدار رجع `2.119.0`، و`dist.integrity` موجود. هذا تحقق من بيانات الحزمة؛ ليس تثبيتًا أو اختبارًا للـCLI أو ثنائيها على Windows.

## 4. مجموعة التجهيز المقترحة التالية

هذه المجموعة المحددة **تحتاج موافقة جديدة** قبل التنفيذ:

1. تنزيل Docker Desktop `4.93.0` من المصدر الرسمي والتحقق من hash والتوقيع.
2. تركيبه للمستخدم الحالي باستخدام WSL 2، ثم بدء Docker والتحقق من اتصال المحرك وإصدار server واختيار Linux containers. الموضع الافتراضي للمستخدم `C:\Users\zyadrady\AppData\Local\Programs\DockerDesktop`؛ بيانات المحرك ينشئها Docker خارج مجلد المشروع.
3. إنشاء مجلد التجربة والملفات المحددة في القسم 2، وتركيب CLI `2.119.0` فيه بإصدار مثبت وlockfile، ثم التأكد من الإصدار وقراءة help.
4. حفظ نتيجة التركيب وفحص جاهزية الأدوات. لا يبدأ `supabase start` أو اختبار الحسابات ضمن هذه المجموعة.

معلمات installer المقترحة من الدليل الرسمي: `install --user --backend=wsl-2 --no-windows-containers`. عند أتمتة التنفيذ تشغل العملية دون نافذة مساعدة ظاهرة إلا إذا احتاج المستخدم التفاعل مع المثبت. قبول شروط استخدام المثبت جزء من خطوة التركيب المقترحة، ولا يشمل شراء اشتراك.

إذا طلب المثبت صلاحيات أدمن أو تفعيل ميزة Windows أو إعادة تشغيل، يسجل السبب ويتوقف الإجراء المعتمد عند هذه النقطة لعرض التغيير؛ لا إعادة تشغيل تلقائية أو تغيير BIOS. تركيب per-user عادة لا يحتاج أدمن، لكن تمكين WSL للمرة الأولى قد يحتاجه؛ WSL موجود هنا بالفعل. [دليل خيارات وصلاحيات التركيب](https://docs.docker.com/desktop/setup/install/windows-install/#administrator-privileges).

الخطة تستعمل أوامر Windows ولا تحتاج ربط Ubuntu بالمشروع. قبل بدء المحرك يراجع إعداد WSL integration في Docker بحيث لا تفعل مشاركة توزيعة Ubuntu القائمة؛ هذا إعداد Docker فقط. لا نثبت Engine داخل Ubuntu أو ننقل المشروع إليها ضمن المجموعة. لم يفحص وجود Docker داخل توزيعة Ubuntu المتوقفة؛ إذا لزم فحصها أو تشغيلها أو تغييرها يعرض ذلك أولًا. لا تمس توزيعة المستخدم القائمة أو بياناتها.

أحجام تنزيل installer وCLI والقرص الافتراضي لم تقس بعد؛ التنزيل المقترح يستخدم الإنترنت وبيانات محلية على C. سحب صور Supabase واستهلاك الحاويات يقعان في الخطوة التالية بعد موافقة مستقلة، وليس في فحص أو تركيب CLI فقط.

## 5. التكلفة وحدود الخطوة

خطة الاستخدام هنا تطوير محلي. دليل Docker يذكر مجانية الاستخدام الشخصي والتعليمي والشركات الصغيرة ضمن شروطه؛ المجموعة المقترحة لا تشمل اختيار خطة مدفوعة. [شروط الاستخدام المختصرة في دليل التركيب](https://docs.docker.com/desktop/setup/install/windows-install/#start-docker-desktop).

لا حساب Supabase سحابي أو مفتاح إنتاج أو ربط مشروع بعيد مطلوب لتركيب CLI وتشغيل التجربة المحلية لاحقًا. لا حساب Bunny أو تجربة خدمة مدفوعة أو نشر. قبول خطة التثبيت لا يعد اعتمادًا لـNext.js أو Vercel أو شراء أي خدمة.

## 6. بعد تركيب الأدوات

تجهز دفعة منفصلة للموافقة، تشمل إعداد مشروع Supabase التجريبي المحلي، تحديد الخدمات والـports والإعدادات، سحب الصور وبدء Auth/Postgres اللازمين للتجربة، وكتابة واختبار المسار المحدود في F01. قبل ذلك تراجع أوامر CLI من help، وملف config الناتج، وحدود الوصول المحلي، ومواضع الأسرار التجريبية.

لا تغلق F01 بنتيجة «Docker يعمل» أو «CLI مثبت». إغلاقها يتطلب أدلة تجربة الحسابات نفسها، خاصة الهاتف دون SMS، استعادة مرة واحدة، ومنع الجلسات القديمة والتجاوز المباشر، كما في T01–T12. التطبيق الكامل وschema النهائية وباقي المراحل لا تبدأ ضمن تركيب الأدوات.

مخرج هذه الدفعة هذه الخطة فقط؛ ملفات المقترح وتقرير الأدوات والمرحلة الأولى والتغييرات السابقة لم تعدل.
