# F01 — نتيجة التسجيل والأعطال والصلاحيات المباشرة

بتاريخ **2026-10-02**، نجحت **12 مجموعة فحص محلية** في آخر تشغيل من **19:13:15 إلى 19:13:32 بتوقيت القاهرة**. تضمنت تسجيلًا كاملًا، طلبات متزامنة، منع التخمين عبر عمليتي خادم، إيقاف العملية فعليًا في **4 مراحل تسجيل و6 مراحل استعادة**، وطلبات مباشرة إلى Auth وData API. أزيلت **15 هوية Auth وهمية** وبياناتها ودور الاتصال المؤقت.

**F01 و2.1 ما زالتا مفتوحتين قبل اعتماد الإنتاج.** كشفت التجربة أن إلغاء جلسات Auth وحده لا يمنع طلب تغيير هاتف اجتاز التحقق قبل الإلغاء. نجح حل محلي يقصر واجهة Auth على خادم المنصة؛ لم يثبت توفير القيد نفسه في Supabase المُدار.

الأدلة: [نتائج الفحوص](F01-registration-results.json)، [فحص الحالة النهائية](F01-registration-verification.json)، [الحالة المضادة قبل حماية Auth](F01-inflight-auth-finding.json). التنفيذ وتعليمات الإعادة في [مجلد التجربة](../../experiments/auth-spike/README.ar.md).

## النطاق المنفذ

موافقة المستخدم «ابداء» غطت الدفعة المقترحة بعد [تجربة الاستعادة](F01-recovery-result.ar.md): التسجيل بالاسم والصف والموبايل وكلمة السر، توحيد الهاتف والتكرار، الأعطال والتسوية، منع التخمين، والوصول المباشر إلى البيانات. استُخدمت تعليمات Supabase وأفضل ممارسات Postgres. بقي التنفيذ داخل `experiments/auth-spike` وSQL محلي تجريبي؛ لا مخطط F03 نهائي أو تطبيق إنتاج أو خدمة سحابية.

عملت Postgres `17.11.0.002` وAuth `v2.197.0` وKong `2.8.1` وPostgREST `v16.4` على Docker المحلي، بأداة Supabase CLI `2.119.0` وNode `22.19.0`. لا مزود SMS أو بريد ولا Storage في هذه الدفعة. موافقة `phone_confirm` تقنية داخل Auth، ولا تثبت ملكية الرقم.

## ما أثبتته الفحوص

| الفحص | الدليل المرصود |
|---|---|
| S01 المدخلات | الاسم والصف والهاتف وكلمة السر مطلوبة. توحّدت 7 صيغ للهاتف المصري، منها الأرقام العربية والفارسية و`00` والمسافات. رُفض الصف غير الموجود، وإرسال دور أدمن، وكلمة السر الضعيفة. |
| S02 التسجيل | نشأت هوية واحدة وملف طالب بالاسم والصف والرقم الموحد، ونجح الدخول بالأرقام العربية وقراءة الملف من جلسة المنصة. لم يلزم بريد أو طلب OTP. |
| S03 التزامن والتكرار | طلبان بصيغتين للرقم أنتجا طلب إنشاء واحدًا إلى Auth؛ كلمة سر الطلب الفائز بقيت صالحة. إعادة نفس الطلب لم تغيرها. اختُبر أيضًا سباق نفس مفتاح الطلب ببيانات مختلفة، مع إجبار الطلبين على الوصول إلى INSERT معًا؛ واحد قُبل والآخر رُفض `409`. |
| S04 Auth المباشر | رُفضت 9 طلبات عميل مباشرة `401`، شملت الدخول وتغييرات الهاتف وكلمة السر والبيانات وOTP والتسجيل وverify وauthorize، حتى مع JWT للمستخدم أو ترويسات مستهلك مزورة. فحص صحة Auth بمفتاح الخادم بقي `200`. |
| S05 صلاحيات البوابة | `/me` مرتبط بصاحب الجلسة؛ رُفض تمرير معرف طالب آخر، ووصول الطالب إلى إجراءات الأدمن. |
| S06 Data API فعلي | PostgREST استجاب `200`. رُفضت 5 طلبات بــJWT صالح: قراءة ملف الطالب نفسه أو غيره، تعديل الدور، قراءة طلبات التسجيل، واستدعاء RPC. كلها `403` ورمز Postgres `42501`. |
| S07 تخمين الدخول | عمليتا Node مختلفتان أرسلتا 6 طلبات معًا: 3 وصلت لفحص الدخول و3 رُفضت `429`. إيقاف عملية وإعادة تشغيلها لم يمسح الحد. تجاهلت البوابة `X-Forwarded-For` المزوّر؛ أرسلت `Retry-After`، وعاد الدخول بعد إنهاء نافذة fixture. كلمة سر خاطئة ورقم غير معروف أعادا نفس الرد `401`. |
| S08 بقية المداخل | تغيير مفتاح الطلب لم يتجاوز حد التسجيل؛ 3 ردود استقبال و3 ردود `429`. تخمين رمز الاستعادة وcookie تغيير الكلمة وصل إلى الحد أيضًا. عدادات التخمين تحفظ HMAC ولا تحتوي هاتفًا أو IP أو رمزًا خامًا. |
| S09 فشل الملف | أُنشئت هوية Auth حقيقية ثم حُقن فشل قبل الملف. بقيت الهوية مجمدة والدخول مرفوضًا. إعادة الطلب لم تعِد الإنشاء أو كلمة السر. تسوية الأدمن أكملت الملف بالكلمة الأصلية وسجلت هوية المراجع والمرجع والوقت. إعادة التسوية المكتملة لم ترسل تحديثًا إلى Auth. |
| S10 أعطال التسجيل | أُوقفت عملية الخادم بعد حجز الطلب، وبعد إنشاء Auth، وبعد الملف، وبعد فتح المزود. رُفض استيلاء الأدمن على العملية ما دام العامل حيًا؛ بعد إنهائه أمكن التسوية. الحجز الذي لم يرسل أي طلب إلى Auth أُلغي، وأمكن التسجيل بمفتاح جديد. |
| S11 أعطال الاستعادة | أُوقفت العملية بعد التحضير والتجميد وحجز التغيير وتحديث كلمة السر وتسجيل تطبيقها وفتح المزود. رفضت البوابة الجلسة القديمة وcookie الاستعادة القديمة. أعاد الأدمن التجميد وأصدر منحة جديدة مسجلة، ونجح الدخول بكلمة جديدة؛ القديمة ظلت مرفوضة. |
| S12 البيانات والتدقيق | JWT أُلغيت جلسته لم يستطع قراءة البيانات الخاصة. الجداول السبعة جميعها تفرض RLS. دور اتصال البوابة لا يقرأ `auth.users`، وسجل التدقيق خالٍ من كلمات السر والرموز والمفاتيح. |

هذه 12 مجموعة للتجربة، وليست إعلانًا باجتياز اختبارات القبول الأصلية T01–T12 كلها. طلبات HTTP ومزود Auth وقاعدة البيانات فعلية. أعطال العملية تمت بإنهاء عمليات Node مستقلة، والفشل الجزئي في S09 حُقن بعد إنشاء حقيقي ناجح لدى المزود.

## مشكلة الطلب الذي بدأ قبل التجميد

قبل إضافة القيد إلى Kong، حجز الفحص صف المستخدم مؤقتًا، ثم وضع طلب الأدمن لتغيير الكلمة والتجميد أولًا وطلب تغيير الهاتف من JWT القديم بعده. كان طلب المستخدم قد اجتاز التحقق قبل إلغاء الجلسة. بعد تحرير الصف نجح طلب الأدمن `200`، ثم نجح طلب المستخدم `200` وتغير الهاتف. طلب جديد بنفس JWT رُفض بعدها `403 session_not_found`.

**إذن رفض JWT في طلب جديد لا يثبت رفض طلب سبق السماح له.** هذا دليل محلي على الإصدار المختبر، محفوظ كحالة مضادة واضحة، لا كفحص أمني ناجح. مسار تحديث المستخدم في [مصدر Auth v2.197.0](https://github.com/supabase/auth/blob/v2.197.0/internal/api/user.go) يساعد على تفسير التسلسل؛ النتيجة اعتمدت على طلبات فعلية.

المعالجة المحلية تقصر خدمات Auth الأربع الموجودة في Kong على مفتاح الخادم، باستخدام [Key Authentication](https://developer.konghq.com/plugins/key-auth/) و[ACL](https://developer.konghq.com/plugins/acl/). حمّل المشغّل الإعداد الفعلي عبر Admin API `/config` وفق [تشغيل Kong دون قاعدة بيانات](https://developer.konghq.com/gateway/db-less-mode/)، ثم اختبر دخولًا عامًا مرفوضًا وصحة الخادم المقبولة. إعادة تحميل nginx وحدها لا تكفي لإثبات تفعيل هذا الإعداد.

البوابة هي التي تتحكم في التسجيل والدخول والاستعادة، ولا تعطي المتصفح مفتاح الخادم أو جلسة Auth. إجراءات الاستعادة والتسوية تعيد الهاتف إلى القيمة الموثوقة أيضًا. لا تدّعي هذه المعالجة إلغاء طلبات سبق دخولها قبل تغيير حدود الشبكة؛ الانتقال إلى إعداد جديد يحتاج سياسة تصريف أو إيقاف تلك الطلبات.

هذا الحل يعتمد على امتلاك بوابة Auth التي يستطيع العميل الوصول إليها. وضع بوابة أمام مشروع Supabase مُدار لا يثبت وحده منع استخدام عنوان المشروع الأصلي مباشرة. لذلك **حسم طريقة تشغيل Auth مطلوب قبل اعتماد التقنية**.

## التزامن والتسوية وحدود الطلبات

طلب التسجيل يحجز الرقم والمعرف المختار للهوية تحت قيود قاعدة البيانات قبل مخاطبة Auth. مفتاح إعادة الطلب UUID يُحفظ كبصمة، والرد العام `202 registrationReceived` لا يكشف وجود الرقم. هو تأكيد استلام، ولا يعني أن طلبًا غير مؤكد اكتمل. تغيير البيانات غير السرية لنفس المفتاح يرفض `409`؛ كلمة السر لا تُخزن لإعادة التشغيل ولا يعاد إرسالها عند تكرار الطلب.

قفل PostgreSQL استشاري على اتصال مخصص يغطي عملية المزود لكل حساب عبر عمليات Node المختلفة. معاملات الصفوف قصيرة وتنتهي قبل طلبات الشبكة؛ موت العامل يغلق الاتصال ويحرر القفل. التسوية تقرأ الحالة مجددًا بعد امتلاك القفل، ولا تفتح حسابًا بسبب إعادة تسوية تسجيل مكتمل. دور الأدمن يستمد من البيانات الموثوقة، والتسوية تسجل مرجع تحقق حضوري.

إذا بدأت محاولة إنشاء Auth ولم يتأكد وجود الهوية بعد العطل، يبقى الطلب للمراجعة ولا يعاد الإنشاء تلقائيًا أو يربط بحساب آخر يحمل نفس الهاتف. تسوية الاستعادة لا تحفظ أو تعيد كلمة سر غير مؤكدة؛ تجمد المزود مجددًا وتلغي المنحة القديمة وتصدر منحة مختلفة.

عدادات الطلبات مشتركة في Postgres وتستخدم مفتاح HMAC ثابتًا مشتركًا ونطاقًا ثابتًا بين العمال. الخادم يرفض تهيئة limiter دونهما. حدود التجربة ونافذتها وأسماء الصفوف وكلمة السر وسياسة الجلسات ما زالت قيم نموذج، وتحتاج قرارًا للإنتاج. استعمال عنوان اتصال socket مناسب للفحص المباشر المحلي؛ سياسة عنوان العميل خلف proxy موثوق وحماية هجمات موزعة لم تختبر هنا.

## Data API والحالة النهائية

أُضيفت schema الخاصة عمدًا إلى إعداد PostgREST **لإجبار اختبار رفض الصلاحيات من خلال HTTP**، دون منح أدوار العميل استخدامها. لا تعتمد حماية البيانات على استبعاد اسم schema وحده. هذه الحدود المختلفة موضحة في [تأمين Data API لدى Supabase](https://supabase.com/docs/guides/api/securing-your-api). هذا إعداد فحص سلبي، وليس تصميم API المنتج.

فحص الحالة النهائية نجح، ووجد:

- صفر حسابات وبيانات تسجيل وجلسات ومنح وتدقيق وعدّادات وهمية، وصفر أدوار اتصال مؤقتة. بقيت صفّان لإعداد صفوف fixture فقط.
- سبعة جداول مع RLS مفعلة ومفروضة، ودور الخادم بلا LOGIN أو superuser أو BYPASSRLS. `anon` و`authenticated` و`service_role` بلا USAGE على schema الخاصة.
- Postgres وAuth وKong بحالة `healthy`؛ PostgREST يعمل وأكد HTTP جاهزيته، وصورته لا تملك Docker Healthcheck. Auth وPostgREST بلا منافذ جهاز مباشرة؛ المنافذ المنشورة فقط `127.0.0.1:54321` و`127.0.0.1:54322`.
- Auth العام ما زال يرفض `401`، وصحة Auth من الخادم وData API تعيدان `200`. طلب البيانات الخاصة حتى بــ`service_role` رُفض `403 / 42501`.
- أمر `db advisors --local --type all --level info --fail-on error` انتهى `0`. أعاد JSON فيه **تنبيه PERFORMANCE واحد بمستوى INFO: `unused_index`** على جدول التسجيل؛ لم يكن الرد «لا ملاحظات». احتُفظ به في سجل التحقق. هذا الفحص مكمل للاختبارات المباشرة ولا يثبت إعداد إنتاج.

انتهت خوادم Node وعمال الاختبار، وبقيت خدمات Docker المحلية جاهزة لإعادة الفحص. لا كلمات سر أو cookies أو JWT أو مفاتيح في النتائج. إعدادات Kong الخام ومخرجات CLI التي قد تحمل مفاتيح محلية موجودة فقط تحت `.local` المتجاهل في Git؛ لا مفاتيح إنتاج. التغييرات السابقة في Figma محفوظة.

## المتبقي والخطوة المقترحة

بقي قبول الإعداد المستهدف لـAuth وإغلاق منفذه العام، وسياسة الحالات غير المؤكدة التي لا تظهر فيها هوية المزود، وقيم حدود الطلبات، وHTTPS و`Secure` cookies والتحقق بالمتصفح، وانتهاء وتجديد جلسات الإنتاج. توحيد الهاتف الدولي هنا فحص بنيوي للأرقام فقط، وليس إثبات ملكية أو تحققًا من كل بلد وشبكة. Storage وبيانات المنتج ودورة التعطيل المتزامنة وسجل المنتج الدائم لم تختبر في هذه الدفعة.

**تحديث لاحق:** طلب المستخدم مقارنة الأنسب والتكلفة وتقييم تأجيل الحماية إلى ما قبل الرفع. نُفذت [مقارنة الاستضافة وتوقيت الحماية](F01-hosting-comparison.ar.md)، بمسار مُدار مرشح للبناء مع تكامل حسابات مستقل واختبار الإعداد المستهدف قبل إتاحته لمستخدمين حقيقيين. تسمح الخطة بتأجيل إعداد الاستضافة النهائي، مع إبقاء أساس صلاحيات التطبيق أثناء البناء. هذا ترشيح للمراجعة؛ لا اعتماد نهائي لـAuth أو اشتراك مالي أو إنشاء مشروع سحابي أو بدء F02/F03.
