# F01 — مقترح الحسابات وخطة التجربة

تاريخ المراجعة: **2026-10-02 بتوقيت القاهرة**.

**الحالة الحالية: F01 و2.1 مفتوحتان، والحل غير معتمد للإنتاج.** بعد هذا المقترح نفذت دفعات وافق عليها المستخدم: [الدخول الأساسي](F01-basic-auth-result.ar.md)، و[بوابة الخادم والاستعادة](F01-recovery-result.ar.md)، ثم [التسجيل والأعطال ومنع التخمين والوصول المباشر](F01-registration-result.ar.md). نجحت فحوص الدفعة الأخيرة المحلية، وكشفت مشكلة طلب Auth الذي بدأ قبل تجميد الحساب. نجح قيد Auth على الخادم في Kong المحلي؛ قبول الإعداد المستهدف، وخاصة Supabase المُدار، ما زال مطلوبًا. ما يلي يوثق المقترح ونطاق الموافقة الأصليين؛ schema الحالية نموذج داخل مجلد التجربة فقط، ولا migrations أو مخطط F03 نهائي.

استجابة لطلب المستخدم مقارنة الأنسب والتكلفة وتقييم تأجيل الحماية النهائية، أضيفت [مقارنة الاستضافة وتوقيت الحماية](F01-hosting-comparison.ar.md). توصي بمسار مُدار للبيانات والبناء مع فصل تكامل الحسابات، وتسمح بتأجيل إعداد الاستضافة واختبارها إلى ما قبل الإتاحة الحقيقية؛ لا تؤجل صلاحيات التطبيق أثناء البناء، ولا تعتمد خدمة Auth الإنتاجية أو اشتراكًا ماليًا تلقائيًا.

الإذن لهذه الدفعة: قراءة تعليمات Supabase وتوثيقها الرسمي، وحفظ الحل المقترح وخطة اختباره. رد المستخدم «ابدأ» يخص هذه الإجراءات المحددة. اعتماد الحل أو فحص أدوات الكمبيوتر أو تثبيتها أو تشغيل تجربة أو إنشاء خدمة يحتاج موافقة جديدة، وفق طلب المستخدم السؤال قبل كل خطوة جديدة.

## 1. المطلوب المعتمد

مرجع السلوك: [قرارات المرحلة الأولى](../phase-1/decisions.ar.md) D01/D03/D18/D19/D20/D24، و[معايير القبول](../phase-1/acceptance-criteria.ar.md) AC01/AC02. موضع الدفعة: F01 و2.1 في [خطة التنفيذ](../phase-1/implementation-backlog.ar.md).

- الطالب يسجل باسم وصف وموبايل وكلمة سر؛ يدخل بالموبايل وكلمة سر.
- الأدمن والطالب هما دورا الحسابات. المدرس سجل بيانات وصفحة فقط.
- استعادة الحساب بعد تحقق حضوري في السنتر، بإجراء أدمن مسجل وبيانات مؤقتة؛ معرفة الرقم أو كود الكورس لا تكفي.
- يسمح بالدخول من أكثر من جهاز. جلسة الفيديو الواحدة تُنفذ لاحقًا، بصورة مستقلة عن جلسات الحساب.
- تعطيل الحساب يمنع العمليات ويحفظ التاريخ؛ لا يجمّد مدة الاشتراك.
- Supabase اختيار مبدئي. تفاصيل التطبيق والاستضافة لم تعتمد بعد، ولا خدمة مدفوعة معتمدة لهذه التجربة.

التصميم التالي **اقتراح تنفيذ** لهذه القواعد. تفاصيل السر المؤقت والجلسات وحدود الطلبات تحتاج مراجعة وتجربة، ولا تصبح قرارات منتج جديدة لمجرد كتابتها هنا.

## 2. ما أثبته التوثيق، وما لم يثبته

| الموضوع | الدليل الرسمي | الاستنتاج وحدوده |
|---|---|---|
| الموبايل وكلمة السر | [دليل Password-based Auth](https://supabase.com/docs/guides/auth/passwords)، [signInWithPassword](https://supabase.com/docs/reference/javascript/auth-signinwithpassword) | الهاتف معرف أصلي مدعوم؛ لا يلزم تحويله إلى بريد صناعي. الدليل يربط إعداد SMS بطلب تأكيد الهاتف. نجاح إعداد المشروع المحدد دون أي إرسال يحتاج تجربة. |
| الإنشاء من الخادم | [admin.createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser) | يوفر إنشاء هوية وموافقة تقنية `phone_confirm`، ويقتصر على الخادم. قبول الهاتف بهذه الطريقة لا يثبت أن صاحبه يملك الرقم فعلًا. |
| إعدادات التطوير المحلي | [مرجع CLI config](https://supabase.com/docs/guides/local-development/cli/config#auth.sms.enable_confirmations) | يوجد إعداد لتأكيد الهاتف وإعداد لمنع التسجيل العام ومفاتيح لمزودي SMS. يلزم اختبار تركيبة الإعدادات والإصدارات قبل كتابة ملف تشغيل معتمد. |
| إعادة تعيين كلمة السر | [admin.updateUserById](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid) | يستطيع الخادم تغيير كلمة السر مباشرة. لا نعتبر هذا وحده تنفيذًا لسر استعادة مؤقت، بصلاحية محددة واستخدام واحد. |
| الخروج وإلغاء الجلسات | [Signing out](https://supabase.com/docs/guides/auth/signout)، [User sessions](https://supabase.com/docs/guides/auth/sessions) | إلغاء refresh tokens لا يجعل كل access JWT قديم غير صالح فورًا. احتياج المنصة لمنع العمليات بعد الاستعادة أو التعطيل يستلزم فحص حالة حية. |
| حماية المسارات المباشرة | [Securing your API](https://supabase.com/docs/guides/api/securing-your-api) | منح صلاحيات الجداول وRLS وحدود schemas أجزاء مختلفة. حماية خادم التطبيق لا تمتد تلقائيًا إلى Data API أو Auth أو Storage؛ كل سطح متاح يجب اختباره. |
| تغيير كلمة السر ذاتيًا | [Password security](https://supabase.com/docs/guides/auth/password-security) | يوثق اشتراط كلمة السر الحالية لتغييرها. يُختبر هذا الإعداد ضمن منع استخدام JWT قديم لتغيير كلمة السر مرة أخرى بعد الاستعادة. |

تمت قراءة مهارة Supabase، واستخدام بحث التوثيق الرسمي وقراءة الصفحات. تعذر عرض ملخص `changelog.md` عبر أداة الويب بسبب نوع المحتوى؛ تمت مراجعة [صفحة سجل التغييرات](https://supabase.com/changelog) بدلًا منه. لم يُقرأ إعداد مشروع سحابي أو تُفحص خدمة فعلية. مراجعة الوثائق لا تثبت أن إعدادًا محليًا يطابق إعداد الإنتاج.

## 3. الاختيار المقترح

**الترشيح: Supabase Auth بهاتف أصلي وكلمة سر، والتسجيل من خادم المنصة، واستعادة مؤقتة يديرها التطبيق.** يظل قبول هذا الترشيح مشروطًا باختبارات القسم 8، وبموافقة المستخدم قبل التنفيذ.

| الاختيار | سبب النظر فيه | موقف المقترح |
|---|---|---|
| تسجيل مباشر عبر `signUp` مع عدم تأكيد الهاتف | أقرب للمسار القياسي وأقل كودًا للإنشاء | بديل عند الحاجة، لكنه يحتاج ضوابط تمنع تجاوز تحقق الاسم والصف والموبايل بالتسجيل المباشر عند المزود. تعطيل التأكيد وحده لا ينفذ الاستعادة أو التعطيل. |
| تسجيل عبر خادم المنصة باستخدام `admin.createUser` | نقطة واضحة للتحقق من الحقول وتوحيد الرقم وتعيين دور الطالب وربط ملفه | **المرشح للتجربة**. يجب إثبات أن إنشاء الأدمن يعمل مع منع التسجيل العام، وأن الدخول يعمل دون مزود SMS أو بريد. |

لن ننتقل إلى بديل يطلب SMS أو بريدًا إلزاميًا أو يغير تجربة الطالب دون قرار جديد. فشل التجربة يسجل السبب ثم يعرض البديل المحدد للمراجعة.

### فصل المسؤوليات

المقترح أن يتعامل المتصفح مع API المنصة، وأن يحتفظ الخادم برموز Supabase بعيدًا عن JavaScript في المتصفح. المتصفح يحمل معرف جلسة تطبيق عشوائيًا في cookie محمية؛ تفاصيل التخزين والتشفير والتجديد تُحسم في F02–F04. هذه بنية خادم مقترحة، وليست إعدادًا تلقائيًا لمكتبة Supabase في المتصفح.

| الجزء | مسؤوليته |
|---|---|
| Supabase Auth | هوية الطالب والتحقق من كلمة السر وإصدار رموز المزود. لا نخزن كلمات السر في جداول التطبيق. |
| خادم المنصة | التحقق من المدخلات، جلسات التطبيق، الدور والحالة الحية، الاستعادة المؤقتة، وفحص ملكية كل عملية. |
| بيانات التطبيق | ملف الطالب والدور الموثوق وحالة الحساب وإصدار صلاحية الجلسات وسجل الدعم. أسماء الجداول والقيود النهائية في F03. |
| واجهة الطالب | إدخال البيانات وعرض الرسائل. لا تقرر دور الأدمن أو حالة الحساب أو صلاحية رمز الاستعادة. |

في هذا الترشيح، جداول الحسابات والدعم والجلسات لا تمنح `anon` أو `authenticated` وصولًا مباشرًا. واجهة البيانات المتاحة للأدوار تحدد لاحقًا في F04؛ أي سطح مباشر يحتاج نفس الحماية الحية أو يمنع وصوله. يختبر ذلك حتى باستخدام JWT حصل عليه العميل مباشرة من Auth. إخفاء عنوان Supabase أو مفتاحه العام ليس ضابط صلاحيات.

استخدام cookie يتطلب حماية طلبات التغيير من CSRF وفحص المصدر وإدارة مدة الجلسة من الخادم. هو اقتراح يلزم تنفيذه واختباره؛ لا توجد cookie أو جلسة في المشروع حاليًا.

## 4. التسجيل والدخول

### التسجيل المقترح

1. يستقبل الخادم الاسم والصف والموبايل وكلمة السر، ويتحقق من صف موجود ومن المدخلات. أقل طول مقترح لكلمة السر 8 أحرف، وتراجع السياسة قبل التجربة. لا تحفظ كلمة السر في ملف الطالب أو السجلات.
2. توحد الأرقام العربية والإنجليزية والفواصل المقبولة، ثم يحول الهاتف بواسطة parser إلى صيغة E.164. تفسير الصيغة المحلية المصرية اقتراح مناسب للتجربة؛ قبول الدول الأخرى أو حصرها قرار واجهة لاحق. المدخل غير الصالح يرفض دون تخمين أو اقتطاع.
3. يستعمل نفس الرقم الموحد في التسجيل والدخول والبحث الإداري والاستعادة. التفرد يفرض في قاعدة البيانات، وليس بفحص سابق فقط.
4. يستدعي عميل Auth إداري منفصل `createUser` بهاتف وكلمة سر و`phone_confirm: true`، ثم يربط ملف الطالب والدور الافتراضي «طالب». لا يقبل `role` أو حالة حساب أو صلاحية دعم من الطلب.
5. يمنع تفعيل الجلسة حتى اكتمال الهوية والملف. إنشاء Auth وربط ملف التطبيق عمليتان مختلفتان؛ لا ندعي أنهما معاملة SQL واحدة. الطلب المكرر والفشل الجزئي يعالجان بمعرف عملية وسجل provisioning وإصلاح مقيد، دون حذف حساب قائم أو اعتباره ملكًا لصاحب الطلب بسبب تطابق الرقم.

`phone_confirm: true` هنا قبول تقني مطلوب للمسار، وليس وصفًا لتحقق SMS. لا تعرض الواجهة «رقم موثّق». استعادة الحساب تظل حضورية؛ تصحيح رقم مسجل خطأ لا يسمح بالاستيلاء على حساب موجود أو دمج التاريخ تلقائيًا.

### الدخول والخروج

- الدخول يستعمل `signInWithPassword` بهاتف موحد وكلمة سر. قبل إنشاء جلسة التطبيق يفحص اكتمال الملف وحالة الحساب وإصدار الصلاحية الحي.
- خطأ الدخول العام لا يكشف هل الرقم موجود أم كلمة السر خاطئة؛ أخطاء صيغة الحقول يمكن توضيحها قرب الحقل.
- جهاز جديد ينشئ جلسة مستقلة؛ لا يفعّل إعداد «جلسة Auth واحدة» لتحقيق قيد الفيديو.
- الخروج العادي يبطل جلسة الجهاز. الاستعادة تبطل جلسات الحساب السابقة كلها. نطاق الخروج يحدد صراحة عند التنفيذ لتفادي اعتماد النطاق الافتراضي للمكتبة.
- دور الأدمن يمنح من إجراء تأسيس موثوق بعد موافقة مستقلة؛ لا تسجيل عام يختار هذا الدور. `user_metadata` غير مصدر لصلاحيات الأدمن.

## 5. الاستعادة الحضورية المقترحة

**رمز الاستعادة هو إذن مؤقت لاختيار كلمة سر جديدة، ولا يوضع ككلمة سر دائمة أو مؤقتة داخل Supabase.** هذا يحقق خيار البيانات المؤقتة في D24 مع فصل تغيير كلمة السر عن الوصول للتعلم.

1. الأدمن المصرح له يتحقق من الطالب حضوريًا ويسجل الفاعل والطالب والوقت والسبب ومرجع تحقق مختصر. لا تحفظ صور مستندات أو تفاصيل زائدة بلا حاجة معتمدة.
2. معاملة بيانات تقفل الاستعادة لهذا الطالب، تبطل منح الاستعادة السابقة، وتزيد `auth_epoch` المقترح، وتبطل جلسات التطبيق السابقة. يبدأ قيد أمني يمنع إنشاء جلسة تعلم جديدة إلى أن تكتمل الاستعادة؛ يظل الحساب المعطل معطلًا.
3. ينشأ رمز عشوائي قوي، مقترح 128 بت على الأقل، يظهر للأدمن مرة واحدة لتسليمه حضوريًا. تحفظ بصمته فقط مع الطالب والوقت والحالة. صلاحية 15 دقيقة اقتراح تجربة، وليست مدة معتمدة؛ انتهاء الرمز يترك الاستعادة مقفلة حتى إعادة إصدارها أو إلغائها بإجراء أدمن مسجل.
4. يدخل الطالب الرمز في مسار الاستعادة ويحصل على جلسة محدودة لا تسمح بقراءة نتائج أو مشاهدة أو تفعيل أو إنشاء محاولة. يختار كلمة السر الجديدة؛ الخادم يعيد فحص الموعد والحالة والملكية.
5. حجز المنحة واستهلاكها يخضع لقفل ومعرف عملية: طلبان متزامنان لا ينفذان تغييرين مستقلين. يستدعي الخادم `admin.updateUserById` للطالب المرتبط بالمنحة فقط. `student_id` من العميل لا يحدد الحساب المستهدف.
6. نجاح التغيير ينهي المنحة والجلسة المحدودة، ويثبت سجل نجاح العملية، ويجدد إصدار صلاحية الجلسات. يدخل الطالب بعد ذلك بالموبايل وكلمة السر الجديدة. لا يستعيد حسابًا معطلًا إلى «نشط» ضمنيًا.

طلب المزود وتحديث قاعدة بيانات التطبيق لا يندمجان في معاملة واحدة. يجب تصميم الحالات `issued → claimed → applied → consumed` مع حالات إلغاء وانتهاء ومراجعة عند تعذر معرفة نتيجة الطلب. بعد الحجز لا يجوز أن يؤدي تكرار الطلب إلى اختيار كلمة سر مختلفة؛ النتيجة غير المؤكدة تبقي الوصول مقفولًا وتحتاج تسوية موثوقة أو منحة جديدة. لا تحفظ كلمة السر الجديدة لتسهيل إعادة المحاولة. التصميم التفصيلي ومعالجة الأعطال في التجربة وF03.

السجل يحفظ معرف العملية ونتيجتها؛ لا كلمات سر أو رمز كامل أو JWT أو رابط يحتوي سرًا. إذا استخدم رابط لاحقًا، يلزم منع تسرب السر عبر سجلات العنوان والإحالة. واجهة الأدمن الكاملة للاستعادة تبقى في المرحلة 3.2؛ هذه الدفعة تقترح عقدها وتجربة محدودة فقط.

## 6. منع الجلسات القديمة والتجاوز المباشر

اقتراح `auth_epoch` يعني رقمًا يتغير عند الاستعادة أو الإبطال الشامل؛ تحمل كل جلسة تطبيق نسخته عند إنشائها. كل عملية محمية تعيد التحقق من حالة الحساب ونسخة الجلسة وملكيتها من مصدر حي. JWT صالح التوقيع لا يكفي لتجاوز قيد الاستعادة أو تعطيل الحساب.

هذا يمنع عمليات المنصة من الجلسات القديمة؛ **لا يبطل JWT لدى خدمة Auth بنفسه**. لذلك تشمل التجربة طلبًا مباشرًا لتغيير كلمة السر أو الهاتف أو إضافة وسيلة دخول من JWT قديم بعد الاستعادة. يختبر إعداد اشتراط كلمة السر الحالية وتوقيت إلغاء جلسات المزود. إذا استطاع رمز قديم تغيير الهوية أو تعيين كلمة سر أخرى، فالترشيح لا يجتاز بوابة الاستعادة حتى يحل هذا المسار أيضًا.

تراجع طريقة إلغاء refresh tokens على الإصدار المختار. لا نفترض وجود استدعاء «خروج بكل الجلسات بواسطة user ID»؛ طريقة المزود الموثقة قد تحتاج JWT للمستخدم. لا نحذف صفوف `auth.sessions` يدويًا اعتمادًا على معرفة تركيبها. انتهاء JWT وحده لا يحقق منعًا فوريًا لعمليات المنصة.

فحص الحالة والجلسة يطبق قرب تنفيذ التغيير أيضًا، لحسم سباق عملية جارية مع تعطيل أو بدء استعادة. الإبطال يمنع طلبات لاحقة؛ لا يستطيع سحب بيانات وصلت بالفعل إلى الجهاز.

## 7. ضوابط وإعدادات التجربة المقترحة

- بيانات محلية وهمية، لا بيانات إنتاج ولا مشروع سحابي. تشغيل Supabase محليًا مرشح، بعد فحص جاهزية الأدوات والموافقة على أي تثبيت أو تشغيل لازم.
- لا مزود SMS أو SMTP خارجي ولا مكالمات Bunny. لا أسرار مزودين خارجية في تجربة الحسابات.
- منع التسجيل العام لدى Auth، مع إثبات أن الإنشاء الإداري والدخول بالهاتف يعملان بهذه التركيبة. لا تضبط `auth.sms.enable_signup` بالتخمين؛ يختبر أثره على مسار كلمة السر. لا توجد قيمة مفترضة لمفتاح `auth.sms.enabled` غير مثبت في مرجع CLI الذي قرئ.
- عميل Auth الإداري ومفتاحه يظلان في الخادم، منفصلين عن عميل التحقق من دخول المستخدم. لا `NEXT_PUBLIC_` لسر خدمة، ولا رموز مستخدم في عميل الخدمة العام المشترك.
- رفض تعديل الدور والحالة و`auth_epoch` من الطالب؛ لا استخدام لـ`user_metadata` في منح الصلاحيات. السجل والجلسات والمنح في بيانات غير متاحة للطالب مباشرة.
- حد للطلبات على الرقم الموحد ومصدر الطلب، وعلى إصدار/تجربة الرموز. الأرقام النهائية تقترح أثناء التجربة مع مراعاة أن طلاب السنتر قد يشتركون في عنوان شبكة واحد. لا قفل دائم بسبب محاولات مهاجم.
- يثبت إصدار CLI وSDK وصور التطوير عند التنفيذ، وتحفظ ملفات lock المعنية. لا يعتمد أحدث إصدار متغير بلا تسجيله.

أسماء البيئة الأولية للمراجعة فقط: `SUPABASE_URL`، `SUPABASE_PUBLISHABLE_KEY`، مفتاح إداري سري مناسب للإصدار، ومفتاح حماية تخزين جلسات التطبيق إن احتاج التصميم له. لا قيم أو مفاتيح فعلية بهذه الوثيقة؛ الأسماء النهائية وعزلها في F05 بعد اعتماد التقنية.

## 8. خطة إثبات عملي محدود

بيئة الدليل المقترحة: طالب A، طالب B، أدمن اختبار، صف اختبار، ساعة خادم قابلة للتحكم. لا كورسات فعلية أو بيع أو فيديو مطلوب لتجربة Auth. **كل الصفوف التالية غير منفذة الآن.**

| الاختبار | النتيجة المطلوبة / الدليل المحفوظ |
|---|---|
| T01 إنشاء هاتف وكلمة سر دون خدمات رسائل | حساب A وملفه يكتملان؛ يدخل ويخرج ويدخل ثانية. لا بريد إلزامي ولا طلب إرسال SMS/بريد. تسجل إعدادات وإصدارات التجربة ونتائج الطلبات المنقحة. |
| T02 صيغ الرقم والتزامن | الصيغ العربية/الإنجليزية والمحلية/الدولية المتكافئة تعطي هاتفًا موحدًا واحدًا. طلبان متزامنان لا يخلقان حسابين؛ الطلب الثاني لا يستحوذ على القائم. المدخل غير الصالح يرفض. |
| T03 الفشل الجزئي للتسجيل | انقطاع بين إنشاء Auth والملف، وفقد رد النجاح وتكرار الطلب، لا ينشئ جلسة لملف ناقص أو هوية أخرى؛ إصلاح آمن موثق. |

| T05 دور وأدوار مزيفة | A لا ينفذ استعادة أو يمنح نفسه أدمن؛ إرسال `role` أو تعديل `user_metadata` أو طلب بيانات B يرفض من الخادم. المفتاح الإداري غير موجود في استجابة أو ملف متصفح. |

| T10 تعطيل الحساب | حساب معطل يرفض جلسة جديدة وعمليات محمية حتى برمز قديم؛ الاستعادة لا تعيد تفعيله ولا تمس تاريخ الاشتراك. |

بوابة نجاح F01: اجتياز T01–T12 بأدلة فعلية، خاصة عدم إرسال الرسائل، ومنع الاستيلاء على الدور، واستهلاك الاستعادة مرة واحدة، ورفض الجلسات القديمة والأسطح المباشرة. أي mock للمزود قد يساعد في اختبار أعطال التطبيق، لكنه لا يثبت دعم Supabase لهذا المسار؛ النجاح الأساسي يحتاج Auth حقيقيًا محليًا. بعدها تعرض نتيجة التجربة واعتماد الاختيار، قبل البناء على افتراض نجاحه.

## 9. ما يلي هذه الوثيقة

الخطوة التالية المقترحة للموافقة: **فحص إصدارات وتوفر Node.js وnpm وDocker وSupabase CLI الموجودة، وفحص إمكانية الوصول لمحرك Docker إن كان يعمل، ثم حفظ تقرير جاهزية.** فحص قراءة فقط؛ لا تنزيل أو تثبيت أو تشغيل محرك أو حاويات أو تعديل إعدادات.

بعد التقرير يعرض حجم التجربة وملفاتها وأدواتها المحددة للموافقة قبل أي تشغيل. لا يبدأ F02/F03/F04/F05 أو المرحلة الثالثة ضمن إذن مراجعة هذه الوثيقة. لا ينشأ حساب Bunny أو يبدأ استخدام مدفوع أو نشر، وفق D27. ملفات المرحلة الأولى والتغييرات السابقة لا تعدل بهذه الدفعة.

هذه الدفعة أنتجت المقترح وخطة الدليل فقط؛ كل قرارات التشغيل والتثبيت والتجربة تظل تنتظر موافقة المستخدم.
